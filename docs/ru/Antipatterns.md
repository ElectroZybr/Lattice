# Антипаттерны

Чего не делать — в ядре и в пакетах, которые им пользуются. Правила — в [Rules.md](Rules.md).

## В пакетах

### Своя композиция

**Плохо:** фабрика, реестр или «менеджер» сам создаёт дочерние объекты и решает, что собрать;
`if`/`switch` по режиму внутри объекта.

**Почему:** этих объектов нет в дереве: ни владения, ни зависимостей, ни экспортов, ни замены
реализации.

**Правильно:** объекты создаются в `compose` и функциях вариантов слота; вариант реализации —
`addSlot<API>().choice(...)`.

### Свой Focus

**Плохо:** объект сам выбирает «текущий / активный» объект или ведёт таблицу «объект → объект».

**Почему:** выбор живёт в двух местах и расходится; Context о нём не знает.

**Правильно:** `Focus<T>` / Context; поле с выбором допустимо, только если его присваивает
`configure` из Context.

### Ручной список детей

**Плохо:** собирать вектор детей вручную; объект ведёт свой список (`add`/`remove`, колбеки).

**Почему:** список расходится с деревом.

**Правильно:** `children<T>()` / `collect<T>()` в `configure`; добавить в набор — добавить узел.

### Знание о Lattice в реализации

**Плохо:** реализация хранит builders, `NodeId`, `Ref`, наследуется от классов Lattice.

**Почему:** её нельзя использовать и тестировать без runtime; builder после композиции
недействителен.

**Правильно:** обычный класс с зависимостями в конструкторе; всё о Lattice — в композиции.

### Потерянная зависимость

**Плохо:** `emplace<Consumer>("c", *device)` или `device.get()`.

**Почему:** разыменование теряет идентичность узла — зависимость не записывается.

**Правильно:** передавать handle: `emplace<Consumer>("c", device)` или `device.ref()`.

### Первый попавшийся

**Плохо:** при нескольких кандидатах взять первый.

**Почему:** результат зависит от порядка загрузки; ошибка конфигурации прячется.

**Правильно:** неоднозначность — ошибка со списком кандидатов; выбор — `focus`.

### Параллельное владение

**Плохо:** `std::shared_ptr` для объектов дерева.

**Почему:** объект переживает ветку; retire его не освобождает.

**Правильно:** владеет дерево (`emplace`, общий ресурс — `emplaceShared` + `mount`).

### Ожидание в runtime

**Плохо:** блокировать `maintain` ожиданием готовности.

**Почему:** host-поток обслуживает всё дерево.

**Правильно:** `readyToDestroy`, `onMaintain`: проверять на следующем `maintain`.

## В ядре

### Узел через пользовательский код

**Плохо:** взять `Node&`, вызвать конструктор объекта или композицию, продолжить работать с
той же ссылкой.

**Почему:** пользовательский код создаёт узлы, хранилище реаллоцируется — ссылка висит.

**Правильно:** сохранить `NodeId`, вызвать пользовательский код, получить узел заново.

### Внутренности наружу

**Плохо:** открыть пакетам `NodeRegistry`, `NodeFactory`, `Builder` ради одного удобства.

**Почему:** пакеты начинают обходить композицию и правила владения.

**Правильно:** маленький примитив композиции или view (`ExportsView`, `TreeView`) для
инфраструктуры.

### Механизм «на будущее»

**Плохо:** новый механизм без сценария у потребителя.

**Почему:** API без потребителя угадывается неверно и потом мешает.

**Правильно:** сначала реальный сценарий, затем минимальный примитив и тест.

### Неявное поведение

**Плохо:** автоматическая пересборка, автоматическое построение графа зависимостей, скрытый
service locator.

**Почему:** что произошло и почему, становится непонятно.

**Правильно:** явные шаги (retire → maintain → собрать заново), зависимости через аргументы.
