# Правила разработки ядра

Как менять Lattice. Устройство — в [архитектуре](articles/Architecture.md), чего не делать — в
[антипаттернах](Antipatterns.md).

## Что входит в ядро

- Ядро — маленькие ортогональные примитивы: дерево, владение, Context, lifecycle, пакеты,
  сервисы, экспорты, конвейеры. Предметное поведение (физика, рендер, форматы) — в пакетах
  потребителей.
- Новый механизм — только с реальным сценарием использования у потребителя. Сначала сценарий
  и минимальный API, потом код.
- Удаляй устаревшие пути вместо слоёв совместимости, если явно не попросили иначе.

## Граница с пакетами

- Пакетному коду открыты `NodeBuild`, `NodeConfigure`, handles (`ObjectBuild`, `Ref`, `Focus`,
  `Slot`) и заголовочные контракты. `NodeRegistry`, `NodeFactory`, `Builder` и другие
  внутренности — только инфраструктурному и управляющему коду (CLI, сериализация, бенчи).
- Контракт, который должны реализовывать обычные классы (`TableAPI`, `PipelineAPI`), —
  заголовочный, без линковки runtime.
- Помощники композиции для контракта (`exportTable`, `configurePipelines`) — отдельный
  заголовок `*Exports.hpp`, подключённый в `Composition.hpp`.

## Инварианты

- **Никогда не держи `Node&` или `Node*` через вызов пользовательского кода** (конструкторы,
  композиция, хуки): он может создавать узлы и вызывать реаллокацию хранилища. Сохрани
  `NodeId`, вызови пользовательский код, затем заново получи узел.
- Builders — move-only и только на время композиции; их нельзя сохранять.
- Выбор никогда не делается молча: неоднозначность — ошибка со списком кандидатов.
- Retire завершает транзитивных потребителей; экспорты снимаются до хуков и уничтожения.
- Дерево и Context меняются только на host-потоке.

## Код

- Ошибки — `Lattice::Exception<Owner>`, в файле `using Error = Lattice::Exception<Owner>;`.
- Комментарий — там, где без него непонятно; код не пересказывать.
- Публичные заголовки ставятся под `Lattice/kernel/` и `Lattice/tools/` (см. `xmake.lua`).

## Тесты

- Фреймворк — [lattice-test](../../libs/lattice-test/README.md), заголовок `<lattice-test/Tests.hpp>`.
  Тестовая цель зависит от `lattice-test-main` (стандартный `main`), в файлах тестов `main` нет.
  `lattice-test` не пишет в консоль; запуск наборов — `ltest`. Подробно — [Testing.md](articles/Testing.md).

- Тест инварианта ядра — `tests/<Тема>_tests.cpp`: `TEST(Тема_Что, RuntimeFixture, "описание")`
  над `RuntimeFixture`, без загрузки пакетов; динамические тестовые пакеты — `tests/TestPackages/`.
- Тест библиотеки — в `libs/<имя>/tests/`, цель `<имя>.tests`; корневой `tests/` — только ядро.
- Библиотека: папка, папка кода (путь `#include <имя/...>`), цель и пакет xmake называются
  одинаково, в нижнем регистре через дефис (`lbm-runner`).
- Новая возможность ядра — тест рядом и раздел с примером в [композиции](articles/Composition.md).

## Библиотеки и пакеты xmake

- `libs/` не зависят от runtime; зависимости между ними — в [libs/README.md](../../libs/README.md).
- Рецепты пакетов — `packages/l/<name>/xmake.lua`. Потребитель после правки ядра переставляет
  пакет (`xmake require -f -y <name>`) — см. [сборку](Build.md#потребителям).

## Документация и планы

- Документация — для человека и агента одновременно: понятна с нуля, без истории проекта.
- Механизмы ядра описываются здесь, потребители ссылаются на них, а не пересказывают.
- Планы: [plans/README.md](plans/README.md) — крупные блоки с чекбоксами; у каждого блока свой
  файл в `plans/`: `# Название`, 1–3 строки цели со ссылками, этапы с чекбоксами. Пункты
  отмечаются в файле блока; закрытый блок отмечается и переносится в «Готово» одной строкой.
- Проект подсистемы — статья в `articles/`.
