# История бенчмарков: lattice-benchmarks (`lbm`)

Проект. Цель — хранить результаты запусков бенчмарков, сравнивать любые два запуска и
baseline, находить деградации и коммит, после которого бенч стал медленнее. Запуск и
анализ — самостоятельный инструмент `lbm` рядом с Lattice; позже его можно вынести в
отдельный репозиторий.

## Решения

* **Хранилище — git-репозиторий результатов** `lbm-results/` в папке, где
  запущен `lbm`. Создаётся автоматически при первом сохранении (`git init`). Git даёт
  историю файла, diff двух запусков, теги-baseline, ветки для экспериментов и синхронизацию
  между машинами.
* **Git — хранилище и навигация, а не детектор.** Числа меняются при каждом запуске, и
  текстовый diff трогает почти каждое значение. Деградацию от шума отличает статистика по
  семплам в `lbm`, который читает историю из git.
* **Измерение отделено от хранения и анализа.** Бинарники бенчей остаются наборами
  (suite) и умеют отдавать результат в машиночитаемом виде; `lbm` запускает их отдельным
  процессом (изоляция падений и состояния GPU), сохраняет и анализирует.
* **Git — системная команда** (`git` в `PATH`), без libgit2.

## Модули

| Где | Что | Зависит от |
|---|---|---|
| `libs/lbm-runner` | модель запуска (`RunResult`: окружение + бенчи), запись в TSV, точка входа набора `Benchmarks::main(argc, argv)` (`--list`, `--filter`, `--tsv <файл>`) | SysInfo, Logger |
| `libs/lbm-history` (новая) | репозиторий результатов (раскладка, слияние частичного запуска, коммит с метаданными), чтение TSV и истории, baseline-теги, сравнение и статистика | BmRunner (модель), SysInfo, Logger |
| `libs/lbm-app` (новая), цель `lbm` | CLI lattice-benchmarks: команды, вывод таблиц, конфигурация наборов (`lbm.toml`, свой разбор подмножества TOML) | BmHistory |
| LatticeLab | наборы `*.bench` через `Benchmarks::main`; `lbm-results/` в `.gitignore`; список наборов в конфигурации `lbm` | — |

Зависимости `BmHistory` и `lbm` — только библиотеки `libs/`, без runtime Lattice: вынос в
отдельный репозиторий не потребует переписывания.

## Репозиторий результатов

```text
lbm-results/
├── .git/
└── <machine>/              отпечаток машины: результаты разных машин несравнимы
    ├── machine.toml        процессор, кеши, память, GPU и драйвер, ОС (SysInfo)
    └── <suite>.tsv         файл на набор: строка на значение метрики
```

* **`<machine>`** — `<host>-<короткий хеш>` отпечатка железа и драйверов. Смена драйвера
  или видеокарты — новая папка, а не «деградация». `machine.toml` не меняется, пока не
  поменялось железо.
* **Формат — TSV в длинном виде**, строка на значение. Diff в git построчный и показывает,
  какая метрика какого бенча изменилась; парсер не нужен; файл читается `grep`/`awk`,
  таблицами, pandas, duckdb. Новая метрика, фаза или стадия — новые строки, а не новая
  схема. Двоичные форматы отвергнуты: в git их не прочитать и не сравнить.

```text
group  bench      implementation  params      n        stage        metric                 value    samples          measured
Walls  Constrain  cpu             workers=1   1000000  Time|Phases  Time.median            4.734e7  4.73e7,4.74e7,…  r0012
Walls  Constrain  cpu             workers=16  1000000  Time|Phases  Time.median            3.912e6  3.90e6,3.93e6,…  r0012
Walls  Constrain  gpu             -           1000000  Time|Phases  Execute:constrain@dev  5.20e6   5.19e6,5.21e6,…  r0012
Walls  Constrain  gpu             -           -        compare      crossover:cpu×16       9800     -                r0012
```

* Бенч — работа, `implementation` и `params` — её вариант (`cpu`, `workers=16`).
* Строки отсортированы по `group`, `bench`, `implementation`, `params`, `n`, `stage`,
  `metric`: порядок стабилен,
  diff показывает только изменения. Единицы — в имени метрики или в заголовке схемы
  (нс, байты, Б/с); числа — с фиксированным числом значащих цифр.
* **Семплы** — в колонке `samples` через запятую: без них статистика не отличит
  деградацию от шума. Сводки capability с одним рядом семплов (`Time.min`, `median`,
  `mean`, `perOperation` по `time`) несут семплы этого ряда. Анализ (`fixed`/`per`, рост, `N*` из `Compare`) — строки со стадией
  `analysis`/`compare` и `n = -`.
* **Частичный запуск** (`lbm run Boundaries Walls`) переписывает только строки
  запущенных работ (все их варианты и сравнение), остальные остаются. Колонка `measured` — номер запуска, в котором
  строка измерена: неизменная строка значит «не перезапускали», а не «то же значение».
* **Коммит = один сохранённый запуск.** Время запуска и окружение — в сообщении коммита,
  не в файле. Трейлеры `lbm` читает через `git log --format=%(trailers)`:

```text
lbm: Boundaries Walls (12 benches), r0012

Machine: zybr-desktop-3f9a
Suite: Boundaries.bench
Run: r0012
Code: LatticeLab@4082414d
Code: Lattice@fafc8a4+dirty
Build: release, gcc 15.2, x86_64
Filter: Walls
```

* **История бенча** — версии файла набора, отфильтрованные по его строкам; читаются
  пачкой (`git cat-file --batch`).
* **Baseline** — тег `baseline/<имя>` на коммит результатов (`lbm tag`, как `git tag`; `run --save --tag` ставит его сразу). Сравнение с baseline берёт
  файл той же машины.
* **Чужие машины** — отдельные папки в одном репозитории; синхронизация — обычный
  `git push`/`pull` (позже `lbm sync`).
* **Вывод в другие инструменты** — `lbm show --json`/`--tsv`: JSON только на выходе, не в
  хранилище.

## Окружение запуска

Без окружения результаты несравнимы, поэтому оно записывается в каждом запуске:

* железо и драйверы — SysInfo (`machine.toml`, хеш — в имени папки);
* сборка — компилятор, режим, архитектура (BuildInfo набора);
* код — sha и флаг незакоммиченных правок репозиториев набора. `lbm` определяет их сам по
  пути бинарника (`git -C <repo> rev-parse`, `status --porcelain`); дополнительные
  репозитории (`../Lattice`) — в конфигурации;
* условия — режим частоты процессора (governor), загрузка системы в начале запуска:
  предупреждение, если они мешают измерению.

## Статистика

* **Сравнение A и B** (два запуска, запуск и baseline) по каждому `(бенч, N, метрика)`:
  отношение медиан, доверительный интервал отношения (bootstrap по семплам) и
  Манна–Уитни по семплам. Изменение значимо, если p < 0,01 и выход за порог (по умолчанию
  5 %, настраивается на бенч).
* **Шум.** Коэффициент вариации семплов; нестабильный бенч помечается, его порог
  расширяется, чтобы шум не выглядел деградацией.
* **По истории** — ряд медиан бенча по коммитам одной машины: поиск точки сдвига
  (сначала — окна до и после каждой точки с тем же тестом; позже — E-divisive). Результат
  — коммит результатов и коммит кода (из трейлеров), после которого ряд сдвинулся.
* **Модель, а не только время.** Сравниваются и `fixed`/`per` по фазам и пороги `N*`:
  деградация часто видна в задержке или в цене на элемент, а не в одном числе.

## CLI

```text
lbm list [suite]                                  наборы, группы, бенчи
lbm run <suite> [фильтр] [--save] [-m текст] [--tag имя]   запустить; --save — записать коммит, --tag — пометить
lbm log [--suite s] [--last k] [--all-machines]   сохранённые запуски: номер, дата, набор, фильтр, код, теги
lbm show [rev] [бенч]                             один запуск (по умолчанию последний)
lbm compare [A] [B] | --baseline <тег>            изменения со значимостью: таблица
lbm history <бенч> [--n N] [--metric m] [--last k] ряд по истории, точки сдвига
lbm regressions [--since rev] [--threshold 5%]    что деградировало и с какого коммита
lbm tag [имя [rev]] | tag -d <имя>                теги baseline: список, поставить, удалить
```

* `<suite>` — имя набора или путь к бинарнику. Наборы находятся сами: в xmake-проекте
  это цели `<Name>.bench` (набор `<Name>`), путь к бинарнику — из `xmake show -t`; перед
  `list`/`run` цель собирается (`--no-build` — без сборки).
* Код запуска (трейлеры `Code:`) — репозиторий набора и локальные репозитории пакетов
  xmake-проекта (`xmake repo -l`: для LatticeLab это `../Lattice`).
* `lbm.toml` в папке запуска необязателен: ещё репозитории кода (`code = [...]`), пороги и
  наборы вне xmake (`[suites]`, тогда поиск через xmake не используется).
* Установка из Lattice: `xmake install-lbm` — `~/.local/opt/lattice-benchmarks` (бинарник и его
  библиотеки, `RUNPATH $ORIGIN/../lib`) и ссылка `~/.local/bin/lbm`; дальше `lbm` работает
  в любом xmake-репозитории с целями `*.bench`.
* **Итог `run`** — одна таблица: бенч (один раз на группу строк), `N` (`1K`, `1M`), время,
  время на элемент, разброс (зелёный < 2 %, жёлтый < 5 %, красный), время базы и `Δ`:
  красный `▼` — значимо медленнее, зелёный `▲` — значимо быстрее, серый — в пределах шума
  (`~` — шумный ряд). Строка итога: `1 faster · 0 slower · 11 unchanged`. `--details` —
  доли фаз хоста и время устройства на самом большом `N`, подгонка исполнителей и `N*`.
* **База** — тег `baseline`, если он есть (`--baseline <тег>` — другой); иначе последний
  сохранённый запуск, и об этом пишется «baseline tag not found».
* **Сохранение.** В терминале `run` спрашивает: пока тега `baseline` нет — «сохранить как
  baseline?», потом — «сохранить?»; затем сообщение (что изменилось в коде), как в git.
  `--save [-m текст] [--tag имя]` — без вопросов (CI), `--no-save` — не спрашивать.
* **`compare`** — та же таблица для A → B: по умолчанию `baseline` (иначе предыдущий запуск)
  → последний; `--changed` — только значимые; `--metric <маска>` — список изменений других
  метрик (фазы, счётчики); код возврата 1 при деградации.
* Фильтр — бенч, группа или маска (`Walls/*Gpu`); запуск группы сохраняет и `Compare`.
* Вывод — таблицы в терминале, `--tsv`/`--json` — для других инструментов; позже отчёт HTML.
* Код возврата `lbm regressions` — ненулевой при деградации: годится для CI.

## Открытые вопросы

* **Объём истории.** Семплы — килобайты на бенч; при тысячах запусков git сжимает их
  хорошо, но `lbm history` должен читать версии пачкой (`cat-file --batch`), а не по одной.
  Если файл набора станет слишком большим, его можно разделить по группам без смены формата.
* **Сборка перед запуском** — только для наборов из xmake; наборы из `lbm.toml` запускаются
  как есть.


### Режимы вывода запуска

`lbm run Suite` показывает только прогресс во время измерений, `lbm run Suite -v` —
текст и прогрессбар снизу, `lbm run Suite -vv` — прежний текст без прогрессбара.
Флаги передаются бинарнику набора. При перенаправлении вывода анимация отключается;
итоговая таблица, сравнение и сохранение работают во всех режимах одинаково.
